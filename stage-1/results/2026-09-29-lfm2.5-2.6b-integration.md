# LFM2.5-2.6B TikZ LoRA integration — 2026-09-29

This is an implementation record for the requested `LiquidAI/LFM2.5-2.6B`
checkpoint, not a training result. The config pins Hub revision
`654f9463ce32b05d0429d76fe1f580b27d4c1ac0`. The model uses a hybrid
short-convolution/GQA architecture and is loaded through Unsloth's
`FastLanguageModel` path.

## Stage 1 setup

- Backend: native Unsloth + TRL `SFTTrainer` using the shared Stage 1 runner.
- Method: unquantized BF16 LoRA, rank/alpha 64, dropout 0.
- LoRA module suffixes: `q_proj`, `k_proj`, `v_proj`, `out_proj`, `w1`, `w2`,
  and `w3`; runtime checks require every suffix to exist before attachment and
  every target to produce trainable LoRA weights afterward. The first GPU
  probe proved that Unsloth 2026.9.11 filters LFM's short-convolution
  `in_proj` out during adapter attachment, despite that suffix appearing in
  the upstream recipe, so it is deliberately excluded rather than silently
  accepting a partial adapter.
- Maximum sequence length: 8,192 tokens; the model's declared context limit is
  131,072.
- Dataset: the audited text-to-TikZ export, with assistant-only labels. Images
  are retained for downstream evaluation and are not fed to Stage 1 training.
- Template: LFM2.5 BOS and ChatML message markers, with a direct assistant
  generation prefix and no automatically opened `<think>` block. Literal
  TikZ target text is preserved.
- Environment: separate Python 3.12 lock using Transformers 5.5.0,
  TRL 0.24.0, and Unsloth 2026.9.11.
- Slurm launcher: `unsloth_native/lfm_stage1.sbatch`, one gate per job on one
  RTX PRO 6000, with no separate GPU-job `--mem` request.

## Gates and resume

1. Prepare a new tokenizer-specific directory with
   `configs/lfm2.5-2.6b-lora.yaml`.
2. Run `overfit-100` with `--resume none` and a fresh run directory.
3. If a time limit interrupts the gate, resubmit the same gate with the same
   run directory and `--resume auto`. The shared native runner resumes the
   latest Trainer checkpoint, including optimizer and scheduler state.
4. Run `smoke-1000` in a separate directory after overfit passes.
5. Run the `full` gate in another fresh directory after smoke passes. Here
   `full` is one epoch over the complete eligible split with LoRA enabled; it
   does not mean full-parameter optimization.

GPU probe job `4401416` loaded the pinned model through Unsloth on one RTX PRO
6000 Blackwell GPU, then failed the strict post-attachment check before
training because `in_proj` had no trainable adapter parameters. No optimizer
step ran and no training metric was produced. The seven-target correction is
code-tested but still requires a fresh `overfit-100` GPU gate; assistant-mask,
checkpoint save/resume, and all acceptance gates remain **unverified**.
